# Learn SVG

学习微信公众号 SVG 代码，沉淀知识到知识库。

## 学习法融合说明

本流程融合三种学习法：
- **SQ3R 阅读法**：Survey 浏览 → Question 提问 → Read 精读 → Recite 复述 → Review 复盘
- **费曼学习法**：用三种讲法验证理解，讲不清 = 知识漏洞
- **艾宾浩斯间隔复习**：学新模式时顺带复习相关旧知识，对抗遗忘

## 触发条件

- 用户给代码片段要求分析
- 用户给完整 HTML 文件要求学习
- 用户讨论后要求沉淀知识

## 知识库位置

写入目标：`.Codex/skills/create-svg/references/knowledge/`

## 学习流程

### 第一步：Survey 浏览（建立整体印象）

1. 读取 `.Codex/skills/create-svg/references/knowledge/index.md`，了解当前知识库中已有哪些模式
2. **关联复习**：找出与当前学习内容可能相关的已有模式，用 1-2 句话快速复述其核心要点
   - 复述流畅 → 说明该知识掌握良好
   - 复述卡壳 → 标记该模式需要复习，向用户汇报
3. **快速浏览源代码整体结构**（不逐行）：
   - 看 viewBox 尺寸
   - 看外层 `<section>` 和顶层 `<g>` 的嵌套结构
   - 大致判断有哪些模块
   - 目的：建立整体印象，为下一步提问做准备

### 第二步：Question 提问（给自己设分析目标）

基于浏览的印象，列出自己要搞清楚的问题。这些问题不是问用户的，是给自己的分析清单。

示例：
- 这个动画的触发方式是什么？点击？自动？
- 这个展开效果的高度是怎么算出来的？
- 这里的 `<g>` 嵌套层级是为什么？冒泡触发的路径是什么？
- 这个数值（如 scale 比例、translate 距离）是怎么来的？

**要求**：
- 至少列出 3 个问题
- 问题要具体，不要泛泛（如"这个代码怎么工作的"不算好问题）
- 问题列表本身就是学习成果：下次遇到类似代码，知道该关注什么

**注意**：用户也是学习者，不是答案提供者。问题的答案由 AI 在精读代码时自己寻找，找不到的标"待验证"，不要反过来问用户"这个你知道吗"。

### 第三步：Read 精读（逐行阅读）

带着第二步的问题，逐行阅读每一行代码，不跳过。阅读过程中：
- 理解每个元素的作用
- 理解每个数值的含义
- 理解动画的触发条件和时序
- 重点关注：第二步提出的问题是否在代码中找到了答案
- 不理解的地方标注出来，不能猜测

### 第四步：模块划分

读完代码后，输出整个代码的模块划分：
- 有哪些模块
- 每个模块大概做什么
- 模块之间的嵌套/并列关系

### 第五步：与已有知识对比

拿每个模块去和已有知识对比：
- 如果是已有模式 → 看有没有不同之处值得记录
- 如果是全新模式 → 作为新知识学习
- 一个文件可能包含多个模式，拆开分别处理

### 第六步：识别未知项

列出自己不确定或不理解的内容：
- 第二步提出的问题中，哪些还没找到答案
- 没有推算出来的公式
- 不理解的设计决策
- 需要多个样本交叉验证的结论

**禁止行为**：
- 不能用"设计值"、"经验值"、"大概这个值"来掩盖没推算出来的公式
- 不能在没有验证的情况下下结论
- 不能把从一个样本中观察到的具体数值当作通用知识

**验证方法**：
- 有多个样本时，必须交叉验证公式
- 只有一个样本时，明确标注"待验证"
- 不确定的结论标注"待验证"，不要反过来问用户（用户也是学习者）

### 第七步：Recite 费曼三段式验证（核心理解检验）

向用户汇报分析结论，用三种讲法验证是否真正理解：

**1. 小白讲法**：用完全不懂 SVG 的人能听懂的话解释这个模式
- 不能出现技术术语（如 viewBox、SMIL、animate）
- 如果无法用日常语言讲清楚 → 说明理解还不够透彻

**2. 技术讲法**：用准确的技术术语描述原理
- 可以使用专业术语
- 要讲清楚机制，不是复述代码

**3. 类比讲法**：找一个生活中的类比帮助理解
- 类比要贴切，不能牵强
- 如果找不到合适的类比 → 说明还没抓住本质

**判定规则**：
- 三种讲法都通过 → 理解合格，进入下一步
- 任何一种讲不清 → 标记为知识漏洞 → 回到第三步重新精读代码
- 如果重新精读仍然讲不清 → 向用户提问，承认不理解

向用户确认：「以上三种理解方式，有没有不准确的地方？」

### 第八步：展示待入库条目

向用户展示完整的待写入内容，格式如下：

```markdown
# 模式名称

## 一句话核心
（这个模式的本质是什么，一句话说清楚）

## 原理
（底层逻辑，掰开揉碎讲清楚）

## 核心代码
（干净的可复用代码片段）

## 关键参数
（通用公式、计算方法、怎么选择值 — 不能是具体数值）

## 变体
（同一个套路，举一反三的应用场景）

## 适用场景
（什么时候用这个模式）
```

### 第九步：用户确认后写入

用户确认内容无误后：
1. 写入或更新知识文件（如 `click-expand.md`）
2. 更新 `index.md` 索引（含关联模式列）

### 第十步：Review 复盘

写入完成后，输出复盘总结：

1. **本次收获**：学到了什么新东西？（新模式 / 已有模式的新变体 / 新的理解）
2. **待验证项**：哪些结论还需要更多样本验证？
3. **知识关联**：本次学习的模式和已有知识形成了什么关联？
4. **复习状态**：第一步关联复习中标记的旧知识，是否需要更新？

## 知识文件命名规则

- 按交互模式命名，用英文短横线分隔
- 示例：`click-expand.md`、`sequence-frames.md`、`horizontal-scroll.md`

## 入库原则

- 只存增量：新模式新建文件，变体追加到已有文件
- 不重复：已有内容不重复写入
- 矛盾时保留两种：讨论差异和适用场景，不覆盖
- 核心是原理和参数：必须掰开揉碎理解清楚后再存
- 不存来源信息：不需要记录参考了哪个源文件
- 只存通用原理：不存从单个样本中提取的具体数值
- 公式必须通用：分母/分子用变量表示，不绑定具体数字

## 入库质量自检

写入前必须确认以下全部通过：

- [ ] 原理能脱离源代码独立解释（不看代码也能讲清楚）
- [ ] 关键参数有明确的通用公式（不是从一个样本反推的具体数值）
- [ ] 公式用变量表示，不绑定具体数字（如 viewBox 宽度，不是 750）
- [ ] 核心代码是干净的可复用模板（不是从源文件直接复制的完整代码）
- [ ] 变体之间有明确的差异说明（不是简单罗列）
- [ ] 适用场景描述具体（不是"各种场景都可以用"）
- [ ] 不确定的内容已标注"待验证"或已向用户确认
- [ ] 没有用"设计值"、"经验值"来掩盖未验证的结论
- [ ] 费曼三段式验证全部通过（小白讲法 / 技术讲法 / 类比讲法）
